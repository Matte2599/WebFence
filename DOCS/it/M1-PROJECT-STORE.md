# M1 — Store locale dei progetti

[English](../en/M1-PROJECT-STORE.md) · [Progetto e autorizzazione](M1-PROJECT-AUTHORIZATION.md) · [ADR SQLite](ADR-004-STORAGE-SIGNATURE.md) · [Roadmap](../ROADMAP.md)

`internal/storage` realizza la **prima persistenza di metadati M1** con SQLite. È un componente Go del core: il desktop non lo invoca ancora e non salva i progetti dell'operatore. Non contiene credenziali, risultati di scansione, prove, report o copie del sito.

## Contratto implementato

`storage.Open(ctx, path)` richiede un percorso assoluto il cui genitore esiste già e crea un file nuovo con permessi `0600` sui sistemi Unix. Rifiuta file non regolari e, su Unix, file esistenti accessibili a gruppo/altri. Chi chiama sceglie e protegge la directory su un filesystem locale affidabile; l'API non definisce ancora la cartella dati dell'app né risolve ogni gara su symlink o ACL Windows. Gli errori pubblici sono codici senza percorso o dati di progetto.

Lo schema **v3** separa `projects` (identità, nome e revisione corrente), `authorization_revisions` (dichiarazioni e stato di revoca immutabili) e `authorization_origins` (origini canoniche ordinate per revisione). Il riferimento all'autorizzazione è testo descrittivo, non il documento originale; rimane comunque metadato potenzialmente sensibile **in chiaro** nel file SQLite. `CreateProject` inserisce la revisione 1 in una transazione; un ID già presente è rifiutato. `LoadProject` e `ListProjects` restituiscono soltanto la revisione corrente con una lettura coerente. `ListAuthorizationRevisions` restituisce dati storici descrittivi, incluso lo stato di revoca, non scope avviabili. Una dichiarazione scaduta o revocata resta leggibile, ma `BeginRun` rifiuta nuove run. `DeleteProject` elimina tutte le revisioni e origini tramite foreign key; non è cancellazione fisica sicura di pagine, WAL, backup o futuri artefatti.

`ReviseAuthorization(ctx, id, expectedRevision, change)` richiede una **nuova dichiarazione esplicita**, confermata e non scaduta, con proprietario, riferimento e insieme completo di origini. Una transazione aggiunge la revisione e sposta il puntatore corrente solo se coincide con `expectedRevision`; un editor che lavora su una versione superata riceve `storage_revision_conflict`. Un rinnovo può partire da un progetto già scaduto o revocato. `RevokeAuthorization(ctx, id, expectedRevision)` aggiunge invece una revisione non avviabile senza cancellare la cronologia; una seconda revoca è rifiutata. Non si modificano le revisioni precedenti e lo snapshot di una run esistente non acquisisce origini o scadenze nuove. Per le run registrate sullo stesso store, [BeginRun e la revoca locale](M1-MANAGED-RUNS.md) fermano il lavoro precedente alla nuova revisione. Un progetto caricato con `LoadProject` e avviato direttamente con `Project.BeginRun()` non è registrato.

All'apertura vengono controllati versione, tabelle richieste, `quick_check` e chiavi esterne; un database sconosciuto o con versione più nuova è rifiutato. Le connessioni usano WAL, `synchronous=FULL`, foreign key attive, `trusted_schema=OFF` e timeout di lock finito. La v3 nasce atomicamente da un file vuoto; i database v1 e v2 sono migrati a v3 in una transazione, mantenendo le dichiarazioni esistenti attive. I test sintetici coprono entrambe le migrazioni, riapertura, conflitto di versione, rinnovo dopo scadenza e revoca, cronologia, snapshot invariato, cancellazione a cascata, rollback a metà inserimento, schemi incompatibili, record alterati e cancellazione del contesto. La CI esegue la suite con race detector sulle piattaforme native configurate.

## Limiti e prossimi passi

Questa è **persistenza di configurazione**, non il flusso completo di M1. Mancano gestione GUI IT/EN, coordinamento delle run tra processi, quota di disco, backup/ripristino verificati, dati di run e risultati, arresto dei futuri job e rimozione dei loro artefatti prima della cancellazione, file di evidenza e rimozione di tutte le copie gestite dall'app. Il filesystem locale e i permessi/ACL su ogni sistema reale richiedono prove dedicate. Non copiare un database aperto ignorando WAL/SHM; la strategia di backup sarà un blocco separato. Nessuna scansione esterna è stata eseguita per queste prove.
