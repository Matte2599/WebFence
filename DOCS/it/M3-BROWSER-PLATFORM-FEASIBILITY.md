# M3 — Fattibilità del confine browser per piattaforma

[English](../en/M3-BROWSER-PLATFORM-FEASIBILITY.md) · [ADR-015](ADR-015-BROWSER-PLATFORM-BOUNDARY.md) · [Stato M3](M3-VALIDATION.md) · [Roadmap](../ROADMAP.md)

Prove locali del 27 settembre 2026 su Apple Silicon/macOS 26.6.2, con sole pagine sintetiche e indirizzi loopback. Le prime prove hanno usato programmi e bundle firmati ad hoc temporanei fuori dal repository; la successiva prova CDP usa materiale versionato, ma non è ancora una scelta di prodotto. Nessun target esterno è stato contattato.

| Prova | Esito osservato | Limite dell'inferenza |
| --- | --- | --- |
| Bundle App Sandbox minimale senza `network.client`, programma Go che apre TCP verso `127.0.0.1:9` | `operation not permitted`; il controllo firmato senza sandbox è eseguibile. | Conferma il divieto TCP nel bundle di prova, non il funzionamento di un motore browser. |

La baseline Ubuntu 24.04.0 usa kernel 6.8 ([Canonical](https://documentation.ubuntu.com/kteam-docs/public/reference/hwe-kernels.html)); la restrizione Landlock per la risoluzione di socket Unix pathname è disponibile solo dall'ABI 9 ([kernel Linux](https://cdn.kernel.org/doc/html/latest/userspace-api/landlock.html)). Aggiornamenti HWE possono cambiare il kernel installato, quindi la capacità va rilevata a runtime. Questa matrice motiva l'[ADR-015](ADR-015-BROWSER-PLATFORM-BOUNDARY.md), ma non chiude la prima voce M3.

Il probe versionato macOS si esegue con `sh experiments/m3-macos-sandbox/run.sh` dalla radice del repository: richiede Go, `codesign` e una copia locale di Chrome nel percorso predefinito, modificabile con `WF_M3_CHROME`. Firma ad hoc un bundle temporaneo senza diritto `network.client`, usa un listener su porta assegnata dal sistema e non apre target esterni. Il comando restituisce codice non zero quando CDP non parte. macOS crea anche il container dell’identificatore di prova `org.webfence.m3-sandbox-probe`; il bundle e il profilo temporanei sono rimossi, mentre la directory gestita dal sistema può restare. Il risultato locale del 29 settembre 2026 è il fallimento riportato nella tabella, non un test di prodotto superato.

Il probe Windows è compilato ed eseguito dal job `m3-windows-appcontainer-lab` della CI su [Windows Server 2022 e Windows 11 ARM64](https://github.com/actions/runner-images?tab=readme-ov-file#available-images). Crea un profilo AppContainer temporaneo senza capacità, usa esclusivamente il listener sintetico locale e richiede che il controllo non confinato si connetta prima della prova nel figlio. Al termine normale richiede l'eliminazione del profilo. La [documentazione Microsoft](https://learn.microsoft.com/en-us/windows/win32/secauthz/implementing-an-appcontainer) descrive la creazione del processo con capacità esplicite; il [loopback degli AppContainer](https://learn.microsoft.com/en-us/windows/security/operating-system-security/network-security/windows-firewall/troubleshooting-uwp-firewall) ha restrizioni proprie. Per questo il timeout osservato non dimostra, da solo, la negazione di Internet o la fattibilità del runtime browser.

## Avvio browser Windows — 29 settembre 2026

Il probe ora accetta `--browser` seguito dal percorso assoluto di Edge o Chrome. Prima conferma il canary AppContainer esistente; poi esegue un controllo browser fuori AppContainer e ripete dentro AppContainer, senza capacità di rete. In entrambi i casi usa un profilo temporaneo separato, un elenco esplicito di handle ereditabili per CDP e diagnostica, un Job Object con **16 processi / 1 GiB**, assegnato prima di riprendere il processo, e una scadenza di 20 secondi. Controlla il token del browser sospeso. Non disabilita la sandbox Chromium. Il test attende `Browser.getVersion`, crea una pagina `about:blank` e verifica una modifica DOM tramite JavaScript.

| Runner | Browser rilevato dal controllo | Controllo CDP/DOM | Browser in AppContainer |
| --- | --- | --- | --- |
| Windows Server 2022 amd64 | Edge 152.0.4191.66 | Passato | Pipe CDP chiusa prima della versione; uscita `0xc0000005`. Causa non identificata. |
| Windows 11 ARM64 | Edge 153.0.4234.48 | Passato | Pipe CDP chiusa prima della versione; uscita `0xc0000005`. Causa non identificata. |
| Entrambi i runner | Chrome 153.0.8010.53 | Passato | Crashpad segnala `CreateNamedPipe: Access is denied (0x5)`; uscita `0x80000003` prima della versione CDP. |

Evidenza: [esecuzione comparativa sul branch](https://github.com/Matte2599/WebFence/actions/runs/36561733556), commit `a60fb62`. L'architettura indicata è quella del runner e del probe Go; non è una verifica dell'architettura dei browser installati. Il log identifica l'operazione fallita in Chrome, ma non prova che correggere quella sola operazione renda sicuro e funzionante il runtime. Le [restrizioni IPC AppContainer](https://learn.microsoft.com/en-us/windows/apps/develop/communication/interprocess-communication) richiedono attenzione al namespace delle pipe. Nessun flag aggiunge permessi di rete o disabilita l'isolamento.

Per Edge/Chrome, la CI ordinaria esegue i test del protocollo, il canary e il controllo positivo Chrome tramite `run-browser.ps1 -ControlOnly -Browser Chrome`. Il workflow manuale **M3 Windows browser feasibility (known unsupported)** esegue anche l'avvio confinato: una mancata risposta resta un job fallito. Una CI ordinaria verde **non certifica questa prova sperimentale**. Una [successiva esecuzione ARM64](https://github.com/Matte2599/WebFence/actions/runs/36563284174/job/109389186163) ha rilevato un timeout di 20 secondi nel controllo Edge dopo la risposta di versione, mentre Chrome ha completato CDP/DOM: la causa non è identificata. Per questo il controllo ordinario usa Chrome; Edge resta nel confronto diagnostico opzionale. `-Browser Chrome` o `-Browser Edge` selezionano esplicitamente un motore nello script; il valore predefinito `All` prova entrambi quelli disponibili. Per riprodurla localmente su Windows, dalla radice del repository:

```powershell
$env:CGO_ENABLED = '0'
go build -o m3-appcontainer.exe ./experiments/m3-windows-appcontainer
if ($LASTEXITCODE -ne 0) { throw 'Lab compilation failed' }
./experiments/m3-windows-appcontainer/run-browser.ps1
```

Il comando cerca i browser già installati nei percorsi standard e restituisce errore se manca un browser o se una prova fallisce. Non installa software. Il profilo temporaneo riceve accesso soltanto per l'AppContainer creato e un'etichetta di integrità bassa; le directory del browser installato non sono modificate. Log e frame CDP sono limitati. I test del protocollo comprendono frame eccessivi, pipe chiusa, errori CDP, sessione/target mancanti ed esecuzione DOM non riuscita.

**Esito della prova Edge/Chrome: avvio confinato non disponibile con quei browser.** Occorre risolvere e riprovare l'inizializzazione IPC del motore dentro il confine prima di collegare broker HTTPS, origine/sessioni e prove negative. Non sono ancora verificati egress generale, servizi locali, quote sotto carico o packaging. Questo blocco non chiude M3 e non costituisce il test complessivo finale.

## Diagnosi macOS successiva

Il 29 settembre sono stati letti il report di arresto locale e gli eventi OS della prova delle 11:02:50 (Chrome PID 75546). La sandbox nega il lookup di `com.apple.coreservices.launchservicesd`; subito dopo `_RegisterApplication` dichiara di non poter ottenere l’identificatore ASN e chiama `abort`. Il report conferma `SIGABRT` nello stack HIServices / `TransformProcessType`. Questo identifica il motivo registrato per quell’avvio: non dimostra che concedere accesso al servizio risolva tutti gli ostacoli o mantenga il divieto di egress attraverso servizi locali. Nessun entitlement è stato ampliato e nessun report di sistema grezzo è stato commesso. Il runtime macOS resta aperto.


## Avvio headless con confine OS esterno

L'[ADR-022](ADR-022-HEADLESS-OUTER-SANDBOX.md) descrive la correzione sperimentale: runtime ufficiale `chrome-headless-shell` fissato, percorsi macOS coerenti con un eseguibile autonomo, IPC Mach limitato al PID e sandbox OS ereditata. App Sandbox/AppContainer sostituiscono in questa prova la sandbox interna Chromium: il laboratorio Linux mantiene la propria configurazione. Il desktop resta Go/Qt Widgets e il browser non viene ancora abilitato nella GUI.

Il probe macOS si esegue con:

```sh
python3 experiments/m3-macos-sandbox/headless_probe.py --runtime-archive /percorso/chrome-headless-shell-mac-arm64.zip
```

L'archivio deve essere quello [ufficiale 154.0.8037.57 mac-arm64](https://storage.googleapis.com/chrome-for-testing-public/154.0.8037.57/mac-arm64/chrome-headless-shell-mac-arm64.zip): lo script verifica l'hash dell'ADR prima di estrarre o eseguire. Non scarica autonomamente, richiede Python 3 e `codesign`, firma solo copie temporanee e usa soltanto fixture locali. Il container OS dell'identificatore di prova può restare, senza profili delle singole run. Il vecchio `run.sh` resta la riproduzione del fallimento con Chrome desktop.

Il nuovo modo Windows è `m3-appcontainer.exe --headless-appcontainer <percorso-assoluto-headless-shell.exe>`. La CI scarica e verifica l'archivio win64 fissato, concede lettura/esecuzione soltanto alla directory temporanea dei file pubblici del runtime e lancia il probe. Il profilo riceve accesso per il SID AppContainer unico; il Job Object mantiene 16 processi/1 GiB. Il nuovo modo non modifica `--browser`, che conserva la prova precedente con sandbox interna.

Le verifiche richiedono CDP e DOM funzionanti, HTTP locale accessibile nel controllo e non contattato dal browser confinato, file esterno negato e file nel profilo leggibile. macOS controlla la sandbox OS dei processi restituiti dal runtime; Windows controlla token, SID, assenza di capacità e appartenenza al Job Object di browser/renderer/GPU/servizio di rete. Il medesimo file esterno è usato prima dal controllo e poi dalla prova confinata; il genitore ne conferma ancora il contenuto. Chromium Windows può riportare `ERR_FILE_NOT_FOUND` quando il percorso non è visibile al processo: il test accetta anche questo esito senza attribuirgli un codice di errore ACL specifico. La regola DNS Windows esclude esplicitamente `127.0.0.1`: senza questa esclusione anche il controllo positivo falliva, quindi il blocco non sarebbe stato prova di AppContainer.

Su macOS 26.6.2 ARM64 la prova completa passa, anche in tre ripetizioni consecutive e con un identificatore di container nuovo. Una variante diagnostica con `network.client` fallisce l'asserzione di rete come richiesto. I job dedicati macOS 15/26 sono passati sul commit `c48fb26`; l'avvio CDP/DOM Windows è passato su entrambi i runner sul commit `a5265a5`. Le prove estese Windows (token/SID/capacità/Job, HTTP e file), senza debugger, sono passate su entrambi i runner nel passo dedicato di [`a5a01d4`](https://github.com/Matte2599/WebFence/actions/runs/36572050007); il controllo Chrome desktop separato di quella run è fallito dopo la riduzione dell’ambiente. Il launcher conserva ora soltanto i percorsi OS necessari a riconoscere la directory predefinita di Chrome, oltre alle variabili minime; non eredita variabili arbitrarie o credenziali. Il controllo Chrome resta un gate CI insieme alle nuove prove headless. Queste evidenze non certificano egress Internet/servizi locali, resistenza a contenuto ostile, quote macOS o distribuzione del runtime; non sono il test conclusivo M3.
